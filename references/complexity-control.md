# Complexity Control

## 复杂度预算

架构的目的不是展示抽象能力，而是把理解、修改和失败限制在可管理边界。评估复杂度时同时计算：

- 组件和平台数量
- 边界与依赖方向
- 状态及合法迁移
- 交互组合、时序和并发
- 版本、权限和环境差异
- 失败恢复与观测成本

跨端或分布式系统的成本主要来自交互项，不等于各端代码量相加。

## 抽象准入测试

引入抽象前回答：

1. 当前至少有哪些真实重复或变化轴？
2. 共同部分的语义是否稳定，还是只有表面相似？
3. 抽象能否减少调用方需要理解的细节？
4. 失败能否更局部，测试能否更独立？
5. 如果未来需求不出现，这个抽象今天仍然值得吗？

若实现需要大量布尔开关、类型判断、例外分支或未使用扩展点，边界通常错误。保留少量清晰重复，可能比错误统一更便宜。

## 分层和依赖方向

- 通用机制下沉：传输、序列化、重试策略、日志、权限适配等不承载业务语义的能力。
- 业务规则停留在能解释其含义的层级，不泄漏到底层通用接口。
- 核心不依赖可选能力；插件、扩展或分析模块单向依赖核心提供的稳定能力。
- 可选组件缺失、旧版或崩溃时，核心路径应明确降级而不是一同失败。

“捕获所有异常并继续”不等于故障隔离。隔离必须保留可观察错误、清晰状态和受控影响面。

## 紧急恢复与长期架构

先验证最小可逆降级：关闭可选能力、回退已知版本、限制流量或切回 Known-Good。恢复核心后，再用复现、失败频率和维护成本判断是否值得引入进程隔离、协议层或更大重构。

沉没成本不能让已写三分之一的架构方案自动成为紧急发布方案。

## 自动化控制阶梯

```text
Known-Good baseline
  → 可观测性完整
  → Shadow Mode（只建议，不控制）
  → 小范围、限幅控制
  → 分阶段扩大权限
  → 持续监控与自动 fallback
```

每一级都有进入门槛、停止条件和回退演练。离线效果优于基线，不足以证明可以直接接管生产。
