# Engineering Principles

## 任务合同

在非平凡修改前，用一页以内回答：

| 字段 | 必须回答的问题 |
|---|---|
| Outcome | 用户或系统最终能观察到什么变化？ |
| Evidence | 什么结果能证明变化成立？ |
| In scope | 允许修改哪些模块、接口、状态或环境？ |
| Out of scope | 哪些行为、兼容性、数据和配置不得改变？ |
| Constraints | 时间、平台、版本、权限和资源上限是什么？ |
| Failure modes | 最可能怎样失败，失败影响到哪里？ |
| Rollback | 如何恢复到已知稳定状态？回退需要多长时间？ |
| Stop conditions | 哪些新事实出现时必须暂停或缩小范围？ |
| Responsibility | 哪些判断必须由人承担，Agent 可以执行什么？ |

合同不是预测完整未来，而是让执行、证据和责任使用同一组边界。

## 目标到执行

1. 从用户可感知结果倒推，不从“要写哪些文件”正推。
2. 识别结果依赖的组件、状态、交互和外部条件。
3. 对每个关键边界列出失败模式和可观察信号。
4. 选择能穿过必要层级的最小端到端闭环。
5. 为闭环定义验证、停止和回退，再拆 Agent 任务。
6. 每个任务只产生一组可独立检查的变化和证据。

## 风险与流程应成比例

低风险、局部、可快速撤销的修改需要轻量合同；生产、数据、权限、跨端状态或不可逆写入需要更强的预览、隔离和回退。不要用重型流程惩罚小修复，也不要用“改动很小”掩盖巨大影响面。

## 决策校准

- **事实**：日志、代码、测试、状态或可复现观察已经证明的内容。
- **推断**：当前最可能的解释，并附带反证方式。
- **未知**：缺失的信息以及它如何限制结论。

直觉可以确定调查顺序，不能决定完成状态。新证据与旧模型冲突时，修改模型、计划或目标，而不是解释掉证据。

## 快速检查

| 决策 | 通过条件 |
|---|---|
| 开始修改 | 现状、范围、证据和回退足够清楚 |
| 扩大范围 | 新范围与目标直接相关，且风险和验证已更新 |
| 增加抽象 | 当前重复、变化轴或故障隔离已经提供证据 |
| 宣布完成 | 目标结果和必要回归有新鲜证据 |
| 保留缓解 | 观测、负责人、复查/退出条件和 fallback 明确 |
