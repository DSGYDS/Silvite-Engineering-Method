# System Thinking

## 五个观察维度

| 维度 | 工程问题 |
|---|---|
| 目标 | 系统究竟要优化什么用户结果或可靠性结果？ |
| 边界 | 哪些组件、数据、环境和参与者属于本次问题？ |
| 约束 | 时间、资源、平台、权限、版本和法规上限是什么？ |
| 激励 | 哪些局部目标可能让参与者或自动系统作出危险选择？ |
| 反馈 | 哪些日志、指标、测试或用户信号会让计划改变？ |

系统图的价值是暴露未知和交互，不是画出漂亮架构。

## 进入陌生技术

先回答以下问题，再决定学习或修改入口：

1. 它位于系统哪一层？
2. 它解决什么问题，输入输出是什么？
3. 上游和下游依赖什么？
4. 它拥有哪些状态、资源和权限？
5. 失败会在哪一层表现，影响到什么？
6. 最小可观察实验是什么？
7. 哪些理论缺口会阻止正确判断？

不要先让 Agent 重写最陌生的层，也不要暂停项目直到学完整个领域。用最小实验定位缺口，补足决定下一步所需的知识，再回系统验证。

## 状态与边界建模

出现以下信号时，考虑显式状态机：

- 多个布尔量组合才能解释当前状态；
- UI、日志和真实业务状态可能不一致；
- 重连、超时、取消、重试或并发操作改变合法迁移；
- 错误恢复依赖“之前发生了什么”；
- 状态需要跨进程、设备或版本同步。

状态机至少定义状态语义、允许迁移、触发事件、超时、错误/恢复路径和可观察输出。不要把 `Connected` 当作业务已经 `Ready` 或 `Streaming` 的证据。

## 跨边界故障

现象出现在哪一端，不代表根因位于哪一端。沿数据和状态路径检查：生产者 → 编码/协议 → 传输 → 接收者 → 消费者，同时考虑版本、权限、时序、重连和用户操作。

优先在边界增加相关 ID、状态转换和时间信息，使一次失败能跨层追踪，而不是在每层独立猜测。

## 模型边界

系统模型是可修改的假设。主动寻找反例，记录预测，事后核验。在没有数据或领域证据时降低结论强度，不用解释力替代事实。
